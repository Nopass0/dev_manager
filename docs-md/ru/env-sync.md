# Единый `.env`

> Раздел: [Документация](./README.md)

Идея: в корне проекта лежит **один** `.env`, в котором переменные сгруппированы
по сервисам секциями. Команда `dm env sync` раскидывает их в `.env` каждого
сервиса.

## Формат единого `.env`

```ini
# Глобальные переменные (без секции) попадают во ВСЕ сервисы.
LOG_LEVEL=info
SECRET_KEY=change-me

# Секция [api] — только для сервиса api.
[api]
DATABASE_URL=postgres://localhost/api
PORT=3001
export DEBUG=true              # поддерживается префикс export

# Секция [web] — только для сервиса web.
[web]
API_URL=http://localhost:3001
```

Правила парсинга:
- строки `[name]` начинают новую секцию;
- `KEY=value` добавляется в текущую секцию;
- пустые строки и `#`-комментарии игнорируются;
- значения в кавычках (`"..."`/`'...'`) очищаются от них;
- поддерживается `export KEY=value`.

## Распределение

```sh
dm env sync
```

Для каждого сервиса формируется `.env` в его каталоге:
- глобальные переменные;
- + сервис-специфичные (перекрывают глобальные при совпадении имён).

Пример вывода:
```
[dm] чтение единого .env: ./.env
  ✓ api: записано 3 переменных в ./services/api/.env
  ✓ web: записано 2 переменных в ./services/web/.env
[dm] синхронизация завершена, обновлено сервисов: 2
```

Сгенерированные файлы помечаются заголовком — не редактируйте их вручную:
```ini
# Этот файл сгенерирован Dev Manager (`dm env sync`). Не редактируйте вручную —
# правьте единый .env в корне проекта и запустите `dm env sync` снова.

LOG_LEVEL=info
DATABASE_URL=postgres://localhost/api
PORT=3001
```

## Поток при разработке

1. Меняете переменную в корневом `.env`.
2. Запускаете `dm env sync` (или добавляете в pre-commit hook).
3. Все сервисы получают актуальные значения.

`dm start` подхватывает `.env` сервисов при запуске процессов — ручное
раскидывание больше не нужно.
