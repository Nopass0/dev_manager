# Single `.env`

> Section: [Documentation](./README.md)

Idea: a **single** `.env` in the project root groups variables by service via
sections. The `dm env sync` command dispatches them into each service's `.env`.

## Format of the single `.env`

```ini
# Global variables (no section) go to EVERY service.
LOG_LEVEL=info
SECRET_KEY=change-me

# Section [api] — only for the api service.
[api]
DATABASE_URL=postgres://localhost/api
PORT=3001
export DEBUG=true              # the export prefix is supported

# Section [web] — only for the web service.
[web]
API_URL=http://localhost:3001
```

Parsing rules:
- lines `[name]` start a new section;
- `KEY=value` is added to the current section;
- blank lines and `#` comments are ignored;
- quoted values (`"..."`/`'...'`) have their quotes stripped;
- `export KEY=value` is supported.

## Dispatch

```sh
dm env sync
```

For each service a `.env` is generated in its directory containing:
- global variables;
- + service-specific ones (overriding globals on name collision).

Example output:
```
[dm] reading single .env: ./.env
  ✓ api: 3 variables written to ./services/api/.env
  ✓ web: 2 variables written to ./services/web/.env
[dm] sync complete, services updated: 2
```

Generated files carry a header — do not edit them by hand:
```ini
# This file is generated by Dev Manager (`dm env sync`). Do not edit by hand —
# edit the single .env in the project root and run `dm env sync` again.

LOG_LEVEL=info
DATABASE_URL=postgres://localhost/api
PORT=3001
```

## Workflow during development

1. Change a variable in the root `.env`.
2. Run `dm env sync` (or wire it into a pre-commit hook).
3. All services pick up the new values.

`dm start` reads each service's `.env` when launching processes — manual
distribution is no longer needed.
